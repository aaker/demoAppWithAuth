Horizon Remote Authentication

End-to-end flow across the SDK app, the Horizon host, ns-api v2, and the remote 3rd-party server.

1. Overview

The flow chains four actors. A remote SDK app (running inside the Horizon host in the browser) asks the host to authenticate it with a 3rd party. The host calls the NetSapiens API (ns-api v2), which mints a short-lived authorization code (with server-side PKCE), then signs and POSTs a webhook to the 3rd party's callback URL. The 3rd party validates the webhook, redeems the code back against ns-api, issues its own access token, and returns it. ns-api relays that token to the host, which stores it and resolves the app's promise.

The key subtlety: /oauth2/remote-auth/initiate is synchronous. ns-api blocks while it POSTs the webhook to the 3rd party; the 3rd party, within that webhook request, redeems the code at /oauth2/token and returns its own token; ns-api then relays that token in the initiate HTTP response.

4. Security mechanisms

4.1 Session authentication (initiate call)

Where: Oauth2Controller::remoteAuth(). How: the initiate request must carry Authorization: Bearer <token> — a NetSapiens JWT or legacy access token, validated first (errors RA001/RA002). JWTs are issued by OauthJwtsTable::generateToken(), signed RS256 (private key + JWKS) or HS256 (per-user + cluster salt); claims include sub (user@domain), domain, user_scope, exp, iat, jti, aud='ns'. Protects: only an authenticated user can initiate, and the code is pinned to that user.

4.2 App permissions & capability gates

Where: HorizonAppsLoader.tsx + PermissionManager.ts. How: the manifest must declare remote-auth:request; PermissionManager also gates route/extension registration per app, and a platform-global toggle can disable a capability for all apps. Protects: an app only invokes surfaces it was granted; no impersonation of another app.

4.3 Callback hostname allow-listing

Where: host pre-check in HorizonAppsLoader.tsx; authoritative check in Oauth2Controller::remoteAuth(). How: the callbackUrl origin is matched against the extension's allowed_hostnames (comma-separated/JSON), exact or wildcard (*.example.com with dot-boundary so evil-example.com is rejected); failures → RA007/RA007B. Protects: the signed webhook (containing the code + verifier) goes only to approved destinations.

4.4 Authorization code

Where: OauthcodesTable::createAuthCode(); oauth_codes table; consumed in _grantByAuthCode. How: random code with client_id=vendorId, redirect_uri=callbackUrl, scope, expires=now+600s, and username bound to the session token's uid (the request body's user.uid is checked, not trusted). The code is deleted after a successful exchange — single use. Protects: short window, binds the grant to the real user, prevents replay.

4.5 Server-side PKCE (S256)

Where: _generateCodeVerifier / _generateCodeChallenge; _validatePKCE. How: ns-api generates both halves — code_verifier = base64url(random_bytes(32)), code_challenge = base64url(SHA256(verifier)). Only the challenge is stored; the verifier is shipped to the 3rd party in the webhook. At token exchange the 3rd party returns the verifier and ns-api validates hash_equals(challenge, base64url(SHA256(verifier))).

Placement note: this is a server-side variant of PKCE. Rather than the public client generating the verifier, ns-api mints it and hands it to the 3rd party over the signed webhook; the 3rd party proves it received that exact webhook by echoing the verifier back.

Protects: ties code redemption to the party that received the webhook; a stolen code alone (without the verifier) cannot be redeemed.

4.6 HMAC webhook signing

Where: sign — Oauth2Controller::remoteAuth() / _sendWebhook; verify — mock-vendor-server/index.js. How: when the extension has a remote_callback_secret, ns-api sends signature = HMAC-SHA256(request_id + code + timestamp, secret) in the body and as X-NS-Signature: sha256=<hex>; the 3rd party recomputes and compares (constant-time); mismatch → 401. Protects: authenticates the webhook as genuinely from NetSapiens and detects tampering.

4.7 RS256 cluster-verification JWT — proves the caller is a genuine NetSapiens server

An optional second proof on the webhook, complementary to the HMAC. Where the HMAC proves "whoever holds the shared secret sent this", this JWT proves "this is a real NetSapiens cluster" and tells the 3rd party which client and cluster it is talking to — with no pre-shared secret.

How ns-api obtains it (the Insight sub-flow):

  • Every NetSapiens server holds a short-lived service token on disk at /etc/netsapiens/insight.d/token.jwt (override: NsInsightTokenPath). This is the cluster's own machine identity to Insight, rotated out of band — not the end-user's session token.
  • When building the webhook, _sendWebhook calls _getClusterVerificationToken($appId) (Oauth2Controller.php L6462). On a cache miss (10-min TTL, keyed per appId) it reads that on-disk token and makes a server-to-server call: POST https://insight.netsapiens.com/getClusterVerificationToken?appId=<appId> with Authorization: Bearer <on-disk service token> (TLS verified, 10s timeout).
  • Insight authenticates the service token and returns { "token": "<RS256 JWT>" }; ns-api caches it 10 minutes and attaches it as the X-NS-Cluster-Verification header (L6580–6582).

What the JWT carries: signed by Insight (RS256) with cluster_id, cluster_name, client, client_id, scope='verification', iss, iat, exp.

What the 3rd party does (optional): verifies it with jwks-rsa against the Insight JWKS endpoint (/.well-known/jwks.json, algorithms: ['RS256']), checking scope === 'verification' and a matching appId. The verified claims confirm the request came from a trusted NetSapiens server and reveal the client name and cluster name. Failure is non-fatal in the mock (HMAC stays primary).

Why two layers: the HMAC secret is shared per-extension and could leak; the cluster JWT is asymmetric (the 3rd party needs only Insight's public keys) and centrally attestable, so a 3rd party can trust "this is NetSapiens, cluster X, client Y" with no prior key exchange.

4.8 Partner / 3rd Party bearer token

Where: mock-vendor-server/index.js /api/user-data. How: the 3rd party issues mock_vendor_token_<random>; protected endpoints require Authorization: Bearer <token> and the server checks prefix + shape (401 otherwise). Protects: gates the 3rd party's own resources behind its issued token.

4.9 Host ↔ app message signing

Where: sdk/security/MessageSigner.ts; used e.g. in DynamicRouteManager.ts. How: host↔app messages can be wrapped as a SignedMessage with _meta {appId, nonce, timestamp, signature}; signature = HMAC-SHA256 (crypto.subtle) over appId|type|payload|nonce|timestamp; verification checks the HMAC, rejects replayed nonces (cleared ~10 min) and enforces timestamp freshness (~5 min, ±1 min skew). Protects: integrity/authenticity of the postMessage-style channel.

4.10 Module-load & API-proxy controls

Where: ModuleLoader.ts, IntegrityValidator.ts, HorizonApiProxy.ts. How: remote-entry scripts load only from approved domains (wildcards, dot-boundary); optional SRI (sha256/384/512 via crypto.subtle.digest) validated before trust; CSP nonce injected on the script tag; rate limiting — module loads 10/min per URL, the per-app API proxy 100/min per app with an audit-log entry per call. Protects: supply-chain integrity of remote bundles and abuse limiting of the API surface.
